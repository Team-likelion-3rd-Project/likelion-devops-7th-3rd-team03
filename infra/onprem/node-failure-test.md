# 온프렘 워커 노드 다운 시험 기록

> 2026-11-09 시험. M6 ON6의 "워커 노드 다운 시험"이다.

[node-maintenance.md](node-maintenance.md)는 **미리 계획한 점검(drain)** 이고, [ON-guide](ON-guide.md)의 F-3은 kubelet만 멈춰서 노드 장애를 **흉내 낸** 시험이다. 이 문서는 **VM 전원을 꺼서 노드가 실제로 사라졌을 때**를 다룬다.
노드 하나가 죽으면 쿠버네티스가 언제 알아차리고, 파드를 언제 옮기고, 서비스가 얼마나 끊기는지를 쟀다.

## 1. 결과 요약

| 시나리오 | 감지 | 파드 이동 시작 | `/api` 중단 | redirect 주소(:30081) 중단 | 프론트 | 복구 후 정리 |
|---|---|---|---|---|---|---|
| A. w2 다운 (DB 아닌 노드) | 38초 | 5분 44초 | 5분 36초 | 5분 46초 | 5초 안팎 끊김만 | 수동 재배치 필요, 3.3 |
| B. w1 다운 (DB 노드) | 33초 | 5분 41초 | 8분 40초 | 8분 38초 | 처음 약 40초 간헐적으로 끊긴 뒤 유지 | w1 복귀 후 mysql +48초, 서비스 +55초 |

- 감지: 전원을 끈 뒤 노드가 `NotReady`가 되기까지.
- 파드 이동 시작: 끈 뒤 죽은 노드의 파드가 `Terminating`이 되기까지. 기본값 `tolerationSeconds: 300`(5분)이 그대로 적용된다.
- 두 시나리오 모두 **노드가 하나 죽으면 앱이 5분 넘게 부분적으로 멈춘다.** 기다리는 5분이 가장 큰 몫이다.
- ON-guide F-3(kubelet 중지)의 실측(약 44초 후 `NotReady`, 약 5분 뒤 퇴출)과 감지, 퇴출 시간이 거의 같다. 이 문서가 새로 보여 주는 것은 노드가 사라진 뒤 서비스가 얼마나 끊기는지와 복귀 후 상태다.

## 2. 시험 방법

- VMware에서 워커 VM을 **Power Off** 했다(정상 종료가 아닌 갑작스러운 정전과 같다).
- cp1에서 [measure.sh](measure.sh)를 돌려 상태 변화를 기록했다. 읽기만 하고 클러스터를 바꾸지 않는다.
  - `http.log`: URL별 HTTP 코드가 바뀐 시각 (`000`은 연결 실패)
  - `state.log`: 노드·파드 상태가 바뀐 시각
  - `top.log`: 30초마다 `kubectl top nodes`
- 확인한 주소: 프론트 `:30080/`, `/api/workspaces`(정상일 때 401), redirect `:30081/`(정상일 때 404), 살아 있는 워커의 `:30080/`.
- **끈 시각과 켠 시각은 사람이 기록하지 못했다.** 첫 실패 로그와 노드가 `Ready`가 된 시각에서 추정한 값이다.

### 시계 오차에 대해
시험 중 cp1의 시계가 실제보다 **약 2일 17시간 44분 느린 채**였다(w1, w2는 정상). 원인은 확인하지 못했고(VM 일시 중지 후 재개로 추정), chrony가 큰 차이를 맞추지 못하고 있었다.
- 시험 B와 1차 w2 시험은 이 상태에서 했다. 시간 간격은 cp1 시계 하나로 쟀으므로 믿을 수 있다.
- 시계를 맞춘 뒤 시험 A를 다시 했더니 감지(36초 vs 38초)와 이동 시작(5분 42초 vs 5분 44초)이 거의 같았다. 시계 오차가 이 간격에 영향을 주지 않았다고 본다. (1차 원본 로그: 첫 실패 06:57:17, `NotReady` 06:57:53, 첫 `Terminating` 07:02:59. cp1 시계 기준)
- 시계를 당긴 직후 약 30분 동안 Argo CD, argo-rollouts, calico-node 등이 한 번씩 재시작했다. 시계 변경과 시각이 맞지만 원인을 확인하지는 못했다.

## 3. 시험 A: w2 다운 (2026-11-09, 시계 정상)

시작 상태: frontend, management, redirect가 w1과 w2에 하나씩, `mysql-0`과 `seaweedfs-0`은 w1, redis는 w2.

### 3.1 시간표 (UTC, 실제 시각)

|---|---|---|

| 02:05:57 | `/api` 503 시작 | +42초 |
| 02:10:59 | w2의 파드 `Terminating` 시작 (퇴출) | +5분 44초 |

### 3.2 노드가 죽은 동안

- **`/api` 중단 5분 36초(02:05:57~02:11:33).** w1의 management와 redirect 파드는 멀쩡히 돌았지만 `Ready`가 아니었다. 헬스 체크가 redis를 포함해서, redis가 죽은 w2에 있으면 `Readiness probe failed: 503`이 된다. management 로그에 `Redis command timed out`(`INFO` 명령, 500ms 초과)이 찍혔다. 같은 날 redis만 0개로 줄여 재현했더니(`kubectl -n snipy scale deploy redis --replicas=0`) 2일 넘게 멀쩡하던 management 파드가 `0/1`, redirect가 `1/2`가 되고 `/api`가 503이었다. redis를 1개로 되돌리자 약 1분 안에 모두 정상이 됐다. redirect도 같은 원인이다.
- 프론트는 w1에 남은 파드가 계속 응답했다. 다만 NodePort가 죽은 w2의 ingress 파드로 가는 순간에는 5초 안팎 끊겼다.
- **`seaweedfs-0`이 w1에서 선점(`Preempted`)으로 내려갔다.** w2에서 옮겨 온 `metrics-server`(우선순위 `system-cluster-critical`)가 w1에 자리가 없어 `seaweedfs-0`을 밀어냈다. w1의 메모리 requests는 3132Mi(98%)였다. `seaweedfs-0`은 볼륨이 w1에 묶여 있어서 w1에서만 다시 뜰 수 있는데 자리가 없어 `Pending`이 됐다.
- **w1이 거의 멈췄다.** w2 복귀 직후 w1에서 `load average 42.89 / 33.42 / 23.39`(코어 2개), 메모리 available 249MB, 버퍼/캐시 313MB였다. `dmesg`에 OOM 기록은 없었다. 이 때문에 w1의 calico-node가 localhost 활성 점검(`liveness`)에서 시간 초과로 재시작을 반복했고(재시작 횟수 47 → 52), 새로 뜬 파드는 서비스 주소(`10.96.0.1:443`, DNS)에 못 붙었다. (metrics-server `i/o timeout`, 프론트 nginx `host not found in upstream`) 부하와 메모리 수치는 직접 쟀고, "메모리 부족이 부하의 원인"이라는 연결은 추정이다.
- w2에서 새로 뜬 management, redirect는 `Unable to determine Dialect without JDBC metadata`로 `CrashLoopBackOff`를 반복했다. DB에 접속하지 못했다는 뜻이다. 접속 실패의 원인(mysql 부하인지 w1 경로 문제인지)은 가려내지 못했다.

### 3.3 w2가 돌아온 뒤

- w2가 `Ready`로 돌아와도 **파드는 알아서 되돌아가지 않는다.** 02:27에 snipy 파드가 모두 w1에 몰려 있었고 w1은 계속 과부하였다.
- 02:28경 w1의 복제본(redirect, management, frontend 각 1개)을 지워 w2로 옮겼다. 이 직후 02:28~02:33 사이 `:30080`, `/api`, `:30081`이 다시 막혔고 w1이 16초간 `NotReady`가 됐다. 이 두 번째 중단이 삭제 때문인지, 이미 한계였던 w1이 무너진 것인지는 구분하지 못했다.
- `seaweedfs-0`은 02:32 재생성을 거쳐 02:33:09에 `Ready`가 됐다.
- 최종 정상화는 w2 복귀(02:22:39) 후 약 12분 뒤인 02:34:44.

## 4. 시험 B: w1 다운 (DB 노드)

시작 상태: 프론트, management, redirect는 w1과 w2에 하나씩, `mysql-0`과 `seaweedfs-0`은 w1.
(cp1 시계가 틀린 상태였으므로 간격만 적는다.)

- 감지는 33초(`NotReady` 07:42:50)였고, 첫 실패 기준 5분 41초 뒤(07:47:58) 첫 `Terminating`이 나왔다. (cp1 시계 기준)
- **프론트는 처음 약 40초(07:42:27~07:42:52) 간헐적으로 끊긴 뒤 07:42:55부터 계속 200이었다.** ingress 컨트롤러가 양쪽 노드에 하나씩 있어서 살아 있는 쪽이 받았다. 죽은 노드의 컨트롤러는 07:48:00에 `Terminating`이 됐고 대체 파드는 07:48:09에 시작해 07:48:31에 `Ready`가 됐다.
- **`/api`가 약 8분 40초, redirect가 약 8분 38초 막혔다.** DB가 w1에 묶여 있고 `mysql-0`은 StatefulSet이라 **죽은 노드의 파드는 노드가 돌아올 때까지 `Terminating`으로 남고 다시 만들어지지 않는다.** 즉 DB 노드가 죽으면 노드가 돌아올 때까지 DB는 자동 복구되지 않는다.
- 다른 노드로 옮겨 간 management, redirect는 DB 없이 `CrashLoopBackOff`가 됐다 (`state.log`에 16줄, 예: redirect `1/2`, management `0/1`).
- w2는 w1 몫을 받고도 버텼다. `top.log` 기준 파드가 옮겨 온 직후(07:48:59) CPU가 92%까지 올랐다가 46% → 8% → 48%로 내려왔고, 메모리는 60~66%였다. w1은 꺼져 있어 `<unknown>`이다.
- w1이 `Ready`로 돌아온 뒤 `mysql-0`이 약 48초, 서비스가 약 55초 만에 정상이 됐다.

## 5. 발견한 약점과 개선 후보

| 약점 | 근거 | 개선 후보 |
|---|---|---|
| 기본 5분 대기 | 두 시험 모두 퇴출까지 5분 40초대 | `tolerationSeconds`를 줄이기 (예: 60초). 줄이면 일시적 끊김에도 파드가 옮겨지는 부담이 생긴다 |
| redis가 헬스 체크에 포함되고 1개뿐 | A에서 w2가 죽자 w1의 앱 파드까지 503 | 헬스 체크에서 redis 제외(캐시가 죽어도 앱은 준비 상태), 또는 redis 이중화 |
| DB 노드가 죽으면 자동 복구 없음 | B에서 노드 복귀까지 DB 중단 | 복구 절차 문서화, 백업 복원 시간 측정, 장기적으로 복제 구조 |
| 한 워커가 죽으면 남은 워커가 한계 | A에서 w1 메모리 requests 98%, 부하 42, 선점으로 `seaweedfs-0` 중단 | 이슈 #295(용량), `seaweedfs`/`mysql`에 `priorityClass` 부여, 워커 메모리 증설 |
| 노드가 돌아와도 재배치 안 됨 | A에서 02:27에 전부 w1에 몰림 | 복귀 후 절차에 재배치 단계 추가(한 번에 하나씩 삭제), 또는 descheduler 검토 |
| 시계 동기화 | cp1이 2일 17시간 44분 늦음 | chrony 설정 점검, 시험 전 `date -u` 확인 항목 추가 |
| 복구 후 하나씩 재시작되는 파드 | 복귀 직후 A에서 w1 파드들이 재시작 | 복귀 직후 과부하를 줄이는 순서(수동 재배치를 천천히) |

## 6. 한계

- 끈 시각과 켠 시각은 사람이 재지 않고 로그에서 추정했다 (오차 약 5~10초).
- 시험 B와 1차 w2 시험은 cp1 시계 오차 상태에서 했다. 간격은 믿을 수 있으나 절대 시각은 실제와 다르다.
- 1차 w2 시험에서는 `/api`를 재지 않았다.
- `kubectl top`이 시험 중 `Metrics API not available`이라(metrics-server가 죽은 노드에 있었다) CPU, 메모리 사용량 로그(`top.log`)가 비었거나 부족하다.
- 이 문서의 수치는 작성 후 원본 로그(`/tmp/measure-074155`, `/tmp/measure-065452`)와 다시 대조해 고쳤다.
- 시험은 각 시나리오당 한 번씩만 했다. 배치(특히 redis 위치)에 따라 결과가 달라질 수 있어서, 같은 시나리오라도 값이 다를 수 있다.
